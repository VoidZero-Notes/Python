# 三层架构

> 三层架构不是一次性设计出来的，而是在实践中不断暴露问题、不断改良的产物。下面按演进顺序梳理：经典三层 → 模型分化 → 依赖倒置 → 当前的实践形态。每一步都在解决上一步遗留的问题，同时也带来新的问题。

## 经典三层架构

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-18-151928.png" alt="image-20260624110412929" style="zoom:50%;" />

`api` 接收请求、`service` 处理业务逻辑、`dao` 负责数据存取，三层各司其职，但都直接依赖同一个 `model`——这个 `model` 本质上是和数据库表结构一一对应的 PO（Persistent Object）。

**解决的问题：** 把「接收请求」「业务逻辑」「数据存取」拆开，避免所有代码堆在一起、职责不清、改一处牵动全身。

**遗留的问题：** 三层共用一个贴着数据库结构的 `model`，问题都出在这个"共用"上：

- `api` 层直接把这个对象暴露给外部调用方，数据库里的敏感字段（如密码哈希）也可能被原样返回。
- `api` 的返回结构被数据库表结构死死绑住：改一个字段，接口跟着变；接口想加个聚合字段，又得反过来改表结构。
- `service` 层做业务运算时也直接用这个"贴数据库"的对象，业务概念（比如「用户身份」「用户联系方式」）没有独立的结构来表达，都糅在一个大类里。

## 模型分化（DTO / BO / PO）

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-18-151933.png" alt="image-20260624110548259" style="zoom:50%;" />

为了不让三层继续共用一个 `model`，把它按层拆成三种职责不同的数据模型：

- **PO（Persistent Object）**：和数据库表结构一一对应，`dao` 层使用。
- **BO（Business Object）**：面向业务逻辑组织的结构，`service` 层使用，可以把零散字段重新分组、组合。
- **DTO（Data Transfer Object）**：面向外部调用方，`api` 层使用，只暴露对方需要、且允许看到的字段。

示例：同一个用户，从"贴数据库"的单一 `model`，分化成三层各自的模型：

```python
# PO：dao 层持有，和数据库表结构一一对应
class User:
  id: int
  username: str
  password_hash: str  # 存储加密后的密码
  email: str
  phone: str
  created_at: datetime
  updated_at: datetime
  is_deleted: bool  # 软删除标记


# BO：service 层持有，按业务语义重新组织字段
class UserIdentity:
  username: str
  password_hash: str

class UserInfo:
  email: str
  phone: str

class User:
  id: int
  identity: UserIdentity
  info: UserInfo
  created_at: datetime
  updated_at: datetime


# DTO：api 层持有，只暴露外部需要看到的字段
class User:
  id: int
  username: str
  email: str
```

**解决的问题：** 每一层只处理和自己职责相关的字段与结构，数据库表结构、业务逻辑、外部接口三者可以独立变化，互不牵制；敏感字段也不会因为"偷懒复用同一个类"而被意外泄露。

**遗留的问题：** `service` 虽然有了自己的 BO，但获取、保存数据时仍要直接创建具体的 `dao` 类来调用。也就是说，「业务逻辑」这个高层模块，直接依赖了「数据怎么存」这个低层模块的具体实现，带来两个后果：

- 换一种存储方式（比如从 MySQL 换成 Redis，或者加一层缓存），`service` 的代码要跟着改。
- 给 `service` 写单元测试时绕不开真实数据库连接，因为它内部直接创建了具体的 `dao` 实例。

## 依赖倒置（IRepository）

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-18-151939.png" alt="image-20260624112836750" style="zoom:50%;" />

依赖倒置原则（DIP）要求：高层模块和低层模块都不应该依赖具体实现，而应该依赖同一个抽象。做法是让 `service` 层自己定义一个抽象接口 `IRepository`（只描述"需要什么能力"，比如按 id 查询、保存），`dao` 层的具体实现去实现这个接口，而不是反过来由 `service` 直接依赖 `dao`。

图中箭头方向的变化就是"倒置"本身：以前是 `service` 依赖 `dao`；现在是 `dao` 依赖 `service` 里定义的抽象 `IRepository`。

**解决的问题：** `service` 不再关心数据具体怎么存、用什么技术存，只面向自己定义的抽象编程。想换存储实现，另外写一个实现了 `IRepository` 的类替换进去即可；写单元测试时也可以传入一个内存版的假实现，不需要真实数据库。

**遗留的问题：** 多了一层抽象（接口定义 + 依赖注入的组装代码）。对小项目、简单 CRUD 场景来说，投入的复杂度可能大于收益——为了"将来也许要换存储"这种低概率场景，先背上接口、注入、mock 的成本。

## 当前的架构

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-18-151920.png" alt="image-20260618104106899" style="zoom:50%;" />

在实际项目里（尤其是中小型项目），上面几步演进带来的复杂度往往用不上，于是又做了一次务实的简化：

- `dao` 这一层通常直接省略：现代 ORM（如 SQLAlchemy、Django ORM）本身就是对数据库的抽象，直接在 `service` 里用它，耦合成本远低于当年"手写 SQL + 裸连接"的年代，没必要再手动包一层 `dao` + `IRepository`。
- BO / PO 的区分大多合并成一个 `model`：ORM 的 `model` 已经不是数据库字段的裸映射，本身具备一定的业务表达能力，没必要再单独分一层 BO。
- 只在 `api` 这一个边界严格保留 DTO：对外的输入输出契约必须显式定义，其余内部数据在 `model` 和 `service` 之间可以直接传递。

模型分化和依赖倒置要解决的问题（数据结构耦合、存储实现耦合）依然存在，只是现代框架和工具已经在别处（ORM、依赖注入库）把一部分问题接管了，三层架构在实践中因此收敛成一种更轻量的形态：**DTO 负责隔离外部，`model` 承担业务 + 持久化的双重角色，`dao` 能省则省。**

## 小结

| 阶段 | 解决的问题 | 遗留 / 新增的问题 |
| ---- | ---------- | ------------------ |
| 经典三层 | 职责分层（接收请求 / 业务逻辑 / 数据存取） | 三层共用一个 `model`，数据库结构直接暴露给外部 |
| 模型分化（DTO/BO/PO） | 每层用各自的数据模型，互不牵制 | `service` 直接依赖具体 `dao` 实现，难替换、难测试 |
| 依赖倒置（IRepository） | `service` 面向抽象编程，不依赖具体存储实现 | 多一层接口和组装成本，小项目容易过度设计 |
| 当前的架构 | 用 ORM / 依赖注入等现成工具吸收上面的问题，回归轻量 | 分层边界变模糊，规范性依赖团队自律 |
