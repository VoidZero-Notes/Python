# 测试

> 测试无法覆盖所有情况。目标不是「全测」，而是用最少的用例锁住最容易坏、坏了最疼的行为。

## 为什么需要测试框架

手写 `if` / `print` 也能验一次，但撑不住日常开发：

1. **防回归**——改一处坏一片，没测试不敢重构。
2. **保契约**——契约即承诺，测试锁死预期输入输出。
3. **提效率**——验证十次，不如脚本跑一秒。

Python 标准库有 `unittest`，本文用 **pytest**：发现用例、断言、夹具、标记都更省事，生态（`pytest-cov`、`pytest-mock`、FastAPI `TestClient`）也围着它转。

| 能力 | `unittest` | pytest |
| ---- | ---------- | ------ |
| 发现用例 | 继承 `TestCase`，方法名 `test_*` | 普通函数 `test_*` 即可 |
| 断言 | `self.assertEqual(...)` | 直接 `assert` |
| 夹具 | `setUp` / `tearDown` | `@pytest.fixture` |
| 参数化 | 较啰嗦 | `@pytest.mark.parametrize` |

## 开发和测试的顺序

1. **TLD**：Test-Last Development，开发先行，测试后行
2. **TDD**：Test-Driven Development，测试先行，开发后行

TDD 的短循环是：先写一个失败的测试 → 写最少代码让它绿 → 再重构。适合逻辑边界多、输入输出清晰的模块（校验、计费、状态机）。UI 拼装、一次性脚本用 TLD 通常更省时间。

两种顺序都要求：**合并前测试是绿的**。差别只在「测试是设计工具还是验收网」。

## 测试选型

按「隔离程度」从内到外。越往外越像真实系统，越慢、越脆，也越能抓住「拼在一起才出现」的问题。

```text
        /\
       /  \        e2e / 系统测试   少而精，锁业务主链
      /----\
     /      \      集成测试         覆盖率的主力
    /--------\
   /          \    单元测试         复杂/重要的纯逻辑
  /------------\
```

- **单元测试**：屏蔽外部，测试单函数、类

  目录建议：`unit/`

  适用场景：复杂或重要的函数、类

- **集成测试**：多模块、类、函数的交互

  目录建议：`integration/`

  适用场景：核心，达到测试覆盖率的核心手段

- **系统测试**：测试整个真实运行的系统

  目录建议：`e2e` / `system`

  适用场景：必做，通常是测试真实环境的启动是否会带来新问题，走一些 happy path 即可

- **e2e 测试**：在系统测试的基础上，测试某个业务功能链（一个用例跑完整个功能链）

  目录建议：`e2e`

  适用场景：必做，主要业务功能链

- **冒烟测试**：系统的底线 / 红线 / 生命线，冒烟测试未通过可视为灾难性事故

  目录建议：不限（用标记筛，不必单独建目录）

  适用场景：下面的情况满足任意一条，必须设置为冒烟测试
  - **如果这个功能挂了，用户立刻无法完成核心任务**

    登录挂了 → 用户进不来；下单挂了 → 收不到钱；支付回调挂了 → 钱付了但订单没更新

  - **这个功能被 90% 以上的用户每天使用**

    比如「查看商品详情」是电商的高频功能，而「修改收货地址」相对低频

  - **这个功能是其他所有功能的前置依赖**

    比如「获取用户 Token」是所有需要登录接口的前提，如果它挂了，后面几十个接口都测不了

  - **这个功能一旦出错，会造成严重的数据损失或资损**

    比如「扣减库存」不能多扣，「退款」不能多退，这类功能哪怕使用频率不高也要加冒烟

  - **这个功能历史上经常出问题（痛点回归）**

    某个接口特别容易改坏（比如复杂的计算逻辑），即使它不算最核心，也可以加冒烟作为「保险」

> **说明：** 冒烟测试往往不针对新功能，而是已上线、稳定运行一段时间的旧功能。

结合本仓库的包结构，测试目录建议挂在应用包下：

```text
apps/web-service/
├── app/
└── test/
    ├── conftest.py
    ├── unit/
    ├── integration/
    └── e2e/
```

系统测试和 e2e 都偏「真跑」，差别是粒度：系统测试问「进程能不能起来、主路径通不通」；e2e 问「某一条业务链从头到尾对不对」。不必为每个接口都写 e2e。

## pytest 基础

安装（开发依赖，不进运行镜像）：

```shell
uv add --package web-service --dev pytest pytest-cov pytest-mock
```

### 发现规则

pytest 默认收集：

- 文件：`test_*.py` / `*_test.py`
- 函数：`test_*`
- 类：`Test*`（不要写 `__init__`）

```python
# test/unit/test_price.py
def test_discount_applies():
  assert apply_discount(100, 0.8) == 80
```

常用命令：

```shell
uv run --package web-service pytest
uv run --package web-service pytest test/unit
uv run --package web-service pytest -k login
uv run --package web-service pytest -m smoke
uv run --package web-service pytest -x          # 第一次失败就停
uv run --package web-service pytest -vv         # 更详细的失败信息
```

### 断言

pytest 会重写 `assert`，失败时直接打印左右两边的值，不必手写消息。

```python
def test_user_payload():
  user = {"id": 1, "name": "张三"}
  assert user["name"] == "张三"
  assert "email" not in user
```

测「应该抛错」用 `pytest.raises`：

```python
import pytest

def test_empty_phone_raises():
  with pytest.raises(ValueError, match="phone"):
    send_verify_code("")
```

同一逻辑、多组输入用参数化，避免复制粘贴：

```python
import pytest

@pytest.mark.parametrize(
  "price, rate, expected",
  [
    (100, 0.8, 80),
    (100, 1.0, 100),
    (0, 0.5, 0),
  ],
)
def test_discount(price, rate, expected):
  assert apply_discount(price, rate) == expected
```

一条用例尽量只验证一件事。结构用 AAA：Arrange（准备）→ Act（调用）→ Assert（断言）。

### fixture：可复用的准备 / 清理

测试里反复出现的「造客户端、造用户、开事务再回滚」不要写在每个函数里，抽成 fixture。作用域从窄到宽：`function`（默认）→ `class` → `module` → `session`。

```python
import pytest
from fastapi.testclient import TestClient

from app.main import app

@pytest.fixture
def client():
  with TestClient(app) as c:
    yield c
```

跨多个文件共享的 fixture 放 `test/conftest.py`，pytest 会自动加载，测试文件里不用 import。

```python
# test/conftest.py
import pytest
from fastapi.testclient import TestClient

from app.main import app

@pytest.fixture
def client():
  with TestClient(app) as c:
    yield c
```

`yield` 之前是 setup，之后是 teardown。上面这个 `client` 每个用例拿一个客户端，用例结束自动关掉。

> **说明：** FastAPI 的 `TestClient` 在进程内发请求，不占用端口，适合单元 / 集成。真要测「uvicorn 拉起来之后」才上系统测试。

### 配置

在应用包的 `pyproject.toml` 里写 pytest 配置，避免每人一套命令：

```toml
[tool.pytest.ini_options]
testpaths = ["test"]
pythonpath = ["."]
markers = [
  "smoke: 冒烟，核心路径未通过视为事故",
]
```

`pythonpath = ["."]` 让 `from app.main import app` 能解析到 `apps/web-service/app`。未注册的自定义标记会告警，所以 `smoke` 要写进 `markers`。

## 测试手段

外部依赖（短信、支付、OSS、真实 DB）不要在单元 / 集成里真打。替换手段从「假对象」到「带断言的假对象」：

| 手段 | 做什么 | 典型用途 |
| ---- | ------ | -------- |
| **Fake** | 能用的简化实现（内存字典当仓库） | 集成测试里替换 DB / 缓存 |
| **Stub** | 固定返回值，不验证怎么被调用 | 只关心「依赖给了什么，我怎么处理」 |
| **Mock** | 既能定返回值，又能断言调用次数 / 参数 | 关心「有没有按契约去调外部」 |

### Stub 模式

```python
# 假设这是你的业务代码（app/services/sms.py）
class SmsService:
  def send_verify_code(self, phone: str) -> dict:
    # 真实调用第三方短信接口
    return {"code": 123456, "success": True}

# app/routers/login.py
class Login:
  @staticmethod
  def send_verify_code():
    user = get_current_user()
    if not user:
      raise PermissionDenied()
    sms_serv = SmsService()
    return sms_serv.send_verify_code(user.phone)
```

```python
# 定义一个 Stub（测试桩），替换真实短信服务
class SmsServiceStub:
  def send_verify_code(self, phone: str) -> dict:
    # 始终返回固定结果，不真正发短信
    return {"code": 999999, "success": True}

def test_login_with_stub(monkeypatch):
  # 用 Stub 替换真实的 SmsService
  monkeypatch.setattr("app.routers.login.SmsService", SmsServiceStub)

  from app.routers import login
  result = login.Login.send_verify_code()

  assert result["code"] == 999999
  assert result["success"] is True
```

`monkeypatch` 是 pytest 内置 fixture，测完自动还原补丁。`setattr` 要补「被测模块里用的那个名字」：如果 `login.py` 写的是 `from app.services.sms import SmsService`，就该补 `app.routers.login.SmsService`，而不是类的定义处。

### Mock 模式

```python
def test_login_with_mock(mocker):
  # 直接 patch 掉 SmsService 类
  mock_sms_class = mocker.patch("app.routers.login.SmsService")
  # 配置实例方法的返回值
  mock_sms_class.return_value.send_verify_code.return_value = {
    "code": 888888,
    "success": True,
  }

  from app.routers.login import Login
  result = Login.send_verify_code()

  assert result["code"] == 888888
  assert result["success"] is True

  # 验证：获取实例，再验证它的方法被调用了一次
  mock_sms_class.return_value.send_verify_code.assert_called_once()
```

`mocker` 来自 `pytest-mock`，本质是 `unittest.mock`，测完同样自动 undo。

Mock 比 Stub 多的功能：

| 功能 | 说明 | 代码示例 |
| ---- | ---- | -------- |
| **验证调用次数** | 确保方法被调用了 N 次 | `mock.method.assert_called_once()` |
| **验证调用参数** | 检查传入了什么值 | `mock.method.assert_called_with(1, "a")` |
| **验证调用顺序** | 多个调用按预期顺序出现 | `mock.assert_has_calls([call.m1(), call.m2()])` |
| **动态返回不同值** | 每次调用返回不同结果 | `mock.method.side_effect = [1, 2, 3]` |
| **抛出异常** | 模拟异常场景 | `mock.method.side_effect = ValueError("错")` |
| **记录所有调用** | 查看历史调用记录 | `mock.method.call_args_list` |
| **重置调用记录** | 清空历史，重新统计 | `mock.reset_mock()` |

**绝大部分情况下，Mock 可以平替 Stub。** 先 Stub 把路径跑通，需要锁「调了几次、传了什么」再升级成 Mock。不要每个依赖都 Mock：测的是自己的分支，不是第三方 SDK 的实现。

### Fake：可运行的替身

Stub 只给死数据；Fake 是一套能增删改查的简化实现，适合替换仓库：

```python
class InMemoryUserRepo:
  def __init__(self):
    self._items = {}

  def save(self, user: dict) -> dict:
    self._items[user["id"]] = user
    return user

  def get(self, user_id: int) -> dict | None:
    return self._items.get(user_id)

def test_register_then_get():
  repo = InMemoryUserRepo()
  repo.save({"id": 1, "name": "张三"})
  assert repo.get(1)["name"] == "张三"
```

FastAPI 里更干净的做法是覆盖依赖，而不是到处 `patch` 类名（和「依赖注入」那一课的 `override` 同一思路）：

```python
from app.deps import get_user_repo
from app.main import app

def test_register(client):
  repo = InMemoryUserRepo()
  app.dependency_overrides[get_user_repo] = lambda: repo
  try:
    resp = client.post("/users", json={"name": "张三"})
    assert resp.status_code == 200
    assert repo.get(resp.json()["id"])["name"] == "张三"
  finally:
    app.dependency_overrides.clear()
```

`dependency_overrides` 是进程级字典，用例结束务必 `clear()`，否则会漏到下一例。

## 冒烟测试

```python
@pytest.mark.smoke
def test_login_success(client):
  response = client.post(
    "/login",
    json={"email": "test@test.com", "password": "123456"},
  )
  assert response.status_code == 200

def test_login_wrong_password(client):  # 没标记，不算冒烟
  response = client.post(
    "/login",
    json={"email": "test@test.com", "password": "wrong"},
  )
  assert response.status_code == 401
```

只跑冒烟：

```shell
uv run --package web-service pytest -m smoke
```

CI 上建议两档：每次提交跑冒烟（快、失败即停）；合并前再跑全量。

## 测试覆盖率

测试覆盖率 = 运行所有测试用例执行到的代码 / 全量的代码。

有些团队有硬性指标，比如测试覆盖率必须达到 80%，否则无法 PR。

覆盖率是「跑到过」，不是「测对了」。一行断言就能把分支标绿；没断言的执行不算有效测试。把指标用在核心包（`app/services`、计费、权限），不要为了百分比去测 `__init__.py` 和纯配置。

```shell
# 跑测试并统计覆盖率
uv run --package web-service pytest --cov=app --cov-report=term-missing

# 生成 HTML（打开 htmlcov/index.html）
uv run --package web-service pytest --cov=app --cov-report=html
```

`term-missing` 会列出没被执行到的行号。只看总数容易自欺。

单独用 `coverage` 也可以，和 pytest 的关系是：pytest 负责跑，coverage 负责记行。

```shell
coverage report
coverage html
```

## 开发日常

1. 新功能选择 TLD 或 TDD
2. 确保新增或修改的测试脚本通过
3. 确保冒烟测试通过
4. 【可选】确保覆盖率达标
5. 提交 PR
6. 后续进入流水线...[略]

落地时再加两条习惯：

- 修 bug 先补一个会失败的用例，再改代码，避免同一坑踩第二次
- 单测不依赖执行顺序、不共享会变的全局状态；需要隔离就用 fixture 的 teardown 或 `dependency_overrides.clear()`
