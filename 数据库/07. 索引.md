索引（Index）是数据库中最直接、最有效的查询性能手段。同样一条 `SELECT`，有没有合适的索引，耗时可能相差成百上千倍。

## 为什么需要索引

没有索引时，数据库执行 `WHERE` 条件只能做**全表扫描**（Sequential Scan）：从第一行开始逐行读取、逐行判断，直到扫完整张表。表有 50 万行，就要读 50 万行——即使最终只匹配到 1 行。

索引则相当于**书的目录**：要在一本 800 页的书里找「事务隔离级别」，你不会从第 1 页翻起，而是先查目录，看到「第 412 页」，再直接翻过去。索引就是数据库替某一列（或几列）预先建好并持续维护的一份有序目录，查找时先在目录里定位，再按定位结果去表里取数据。

| 方式 | 做法 | 查找 50 万行中的少量数据 |
|---|---|---|
| 全表扫描 | 逐行读取并判断条件 | 读取全部 50 万行 |
| 索引查找 | 先在有序结构中定位，再回表取行 | 只读取少数几个索引块 + 匹配行 |

数据表越大，两者的差距越悬殊。反过来说，表很小的时候，索引带来的收益微乎其微。

## 索引的代价

索引不是免费的。它是一份**独立存储的数据结构**，需要占用磁盘空间；更重要的是，它必须和表数据保持同步——每一次 `INSERT` / `UPDATE` / `DELETE`，数据库除了改表，还要顺带维护该表上的**每一个**索引。

| 收益 | 代价 |
|---|---|
| `WHERE` 条件定位快，避免全表扫描 | 额外占用磁盘空间（大表上的索引可能有几百 MB 甚至更大） |
| `ORDER BY` 可直接利用索引的有序性，省去排序 | 每次写入都要同步更新索引，写入变慢 |
| `JOIN` 时能快速匹配关联行 | 索引越多，写放大越严重，批量导入数据尤其明显 |
| `UNIQUE` 索引顺带保证数据唯一性 | 优化器需要评估更多访问路径，计划生成开销变大 |

所以索引的取舍本质上是**「以写换读」**：牺牲一部分写入性能和存储空间，换取查询性能。

## 创建与管理索引

### 基本创建

```sql
-- 单列索引
CREATE INDEX idx_students_age ON students(age);

-- 指定索引名的通用惯例：idx_表名_列名
CREATE INDEX idx_order_created_at ON "order"(created_at);
```

### 唯一索引

```sql
CREATE UNIQUE INDEX idx_students_email ON students(email);
```

唯一索引在加速查询的同时，会拒绝重复值的写入。

### 不锁表创建：CONCURRENTLY

普通的 `CREATE INDEX` 会持有写锁，建索引期间该表无法写入。生产环境的大表应使用：

```sql
CREATE INDEX CONCURRENTLY idx_order_status ON "order"(status);
```

`CONCURRENTLY` 不阻塞读写，代价是要扫描两遍表、耗时更长，且**不能在事务块内执行**；如果中途失败，会留下一个无效索引，需要手动 `DROP` 后重建。

### 复合索引（多列索引）

```sql
CREATE INDEX idx_order_user_created ON "order"(user_id, created_at);
```

复合索引遵循**最左前缀**原则：上面这个索引能加速 `WHERE user_id = 1`、`WHERE user_id = 1 AND created_at > '2024-06-01'`，但**无法**有效加速只写 `WHERE created_at > '2024-06-01'` 的查询。列的顺序要按「等值条件在前、范围条件在后」来安排。

### 部分索引（带 WHERE 条件的索引）

只为满足条件的行建索引，体积更小、维护更省：

```sql
-- 只对未完成的订单建索引，历史已完成订单不进索引
CREATE INDEX idx_order_pending ON "order"(created_at)
WHERE status = 'pending';
```

适用于「查询总是只关心一小部分行」的场景，比如未处理任务、未删除记录。

### 表达式索引

如果查询里对列做了运算，可以直接为**运算结果**建索引：

```sql
-- 支持 WHERE lower(email) = 'abc@example.com'
CREATE INDEX idx_students_email_lower ON students(lower(email));
```

### 删除与查看

```sql
DROP INDEX idx_students_age;
DROP INDEX IF EXISTS idx_students_age;
DROP INDEX CONCURRENTLY idx_students_age;   -- 同样不阻塞读写
```

在 `psql` 中用元命令查看：

```sql
\di                 -- 列出当前库所有索引
\d students         -- 查看表结构，末尾会列出该表的索引
```

也可以查询系统视图 `pg_indexes`：

```sql
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'order';
```

## 索引类型

PostgreSQL 支持多种索引结构，不同结构擅长的查询类型完全不同。不指定时默认使用 `B-tree`。

| 类型 | 它擅长什么 | 什么场景下用它 |
|---|---|---|
| **B-tree** | 默认类型，支持等值（`=`）、范围（`>` `<` `BETWEEN`）、排序（`ORDER BY`）、最左前缀匹配 | 绝大多数场景，数字、时间、字符串列的常规查询 |
| **Hash** | 只支持等值比较（`=`），不支持范围和排序 | 极少用；只按 `=` 查且不需要排序时，可略省空间 |
| **GIN** | 加速「一个值里包含多个元素」的查询，如全文检索、JSONB、数组包含 | 全文检索、JSON 字段搜索、数组包含查询 |
| **GiST** | 通用可扩展结构，支持几何、范围类型、最近邻和模糊搜索 | 地理位置查询、范围类型重叠判断、相似度搜索 |
| **BRIN** | 轻量级索引，按数据在磁盘上的物理块范围建索引，占用空间极小 | 超大表 + 数据天然有序（如时间序列日志），查范围不查单条 |
| **SP-GiST** | 面向空间可分割的数据结构（如四叉树、前缀树） | 电话号码、IP 前缀、非均衡分布的空间数据等特殊场景 |

指定类型的语法：

```sql
CREATE INDEX idx_order_log_time ON order_log USING BRIN (created_at);
CREATE INDEX idx_product_tags ON product USING GIN (tags);
```

## 主键、唯一约束与索引的关系

PostgreSQL 会为 `PRIMARY KEY` 和 `UNIQUE` 约束**自动创建**对应的唯一索引，不需要也不应该再手动重复建。

```sql
CREATE TABLE students (
  id SERIAL PRIMARY KEY,              -- 自动创建 students_pkey 唯一索引
  name VARCHAR(50) NOT NULL,
  email VARCHAR(100) UNIQUE           -- 自动创建 students_email_key 唯一索引
);

-- 多余，不要写：
-- CREATE INDEX idx_students_id ON students(id);
```

重复建索引不会报错，但会白白占用空间并拖慢写入。需要注意的是，**外键列不会自动建索引**——`user_id` 这类外键列如果经常出现在 `JOIN` 或 `WHERE` 中，应当手动建：

```sql
CREATE INDEX idx_order_user_id ON "order"(user_id);
```

## 用 EXPLAIN 验证索引效果

索引有没有生效，不能靠猜，要用 `EXPLAIN` 看执行计划。

| 命令 | 行为 |
|---|---|
| `EXPLAIN SQL` | 只让优化器**估算**执行计划，不真正执行，输出的是预估值 |
| `EXPLAIN ANALYZE SQL` | **真正执行**这条 SQL，输出预估值与实际耗时、实际行数的对比 |
| `EXPLAIN (ANALYZE, BUFFERS) SQL` | 在上面基础上，额外显示读取了多少数据块、命中缓存多少 |

> **注意：** `EXPLAIN ANALYZE` 会真实执行语句，对 `UPDATE` / `DELETE` 使用时务必放进事务里并回滚。另外，单独的 `ANALYZE 表名` 是**收集统计信息**的维护命令，和 `EXPLAIN ANALYZE` 完全是两回事——统计信息不准会导致优化器选错计划，所以大批量写入后通常要执行一次 `ANALYZE 表名`。

### 读懂执行计划的关键词

| 关键词 | 含义 |
|---|---|
| `Seq Scan` | 全表顺序扫描，逐行读取整张表。大表上出现通常意味着索引缺失或未被使用 |
| `Index Scan` | 走索引定位，再回表取完整行数据。匹配行数较少时最高效 |
| `Index Only Scan` | 需要的列全在索引里，连表都不用回，最快 |
| `Bitmap Heap Scan` | 先用索引收集所有匹配行的位置生成位图，再按物理顺序批量回表。匹配行较多时优于逐行 `Index Scan` |
| `cost=0.00..8.27` | 优化器估算的代价，前者是返回首行的启动代价，后者是返回全部行的总代价（相对单位，不是毫秒） |
| `rows=1234` | 优化器**估算**返回的行数 |
| `actual time=0.015..2.301 rows=1200` | 只在 `ANALYZE` 下出现，是**实际**耗时（毫秒）和实际行数 |
| `Planning Time` / `Execution Time` | 生成计划的耗时 / 实际执行的总耗时 |

判断方法很简单：看 `rows` 的估算值和 `actual` 的实际值是否接近（差太多说明统计信息过期），再看扫描方式是否从 `Seq Scan` 变成了索引扫描。

## 实测演示

下面这段脚本用来直观地感受索引的效果，操作对象是《04. 表间关系》电商 ERD 示例里的 `order` 表（含 `user_id` / `order_no` / `status` / `total_amount` / `created_at` 字段）。注意 `order` 是 SQL 保留字，必须用双引号包起来写成 `"order"`。

脚本做四件事：先用 `generate_series` 造 50 万条分布在两年内的测试订单；在**无索引**状态下用 `EXPLAIN (ANALYZE, BUFFERS)` 查询某个月的订单；然后为 `created_at` 建索引；再用同一条 SQL 查一次做对比。

预期观察到的现象：无索引时执行计划是 `Seq Scan on "order"`，需要读完全部 50 万行，耗时明显；建索引后计划变为 `Index Scan` 或 `Bitmap Heap Scan`（PostgreSQL 会根据匹配行占比自行选择），读取的数据块数量和 `Execution Time` 都大幅下降。

```sql
-- =============================================
-- 索引演示：order.created_at
-- 演示：无索引 vs 有索引（EXPLAIN ANALYZE）
-- =============================================

-- 1. 插入 50 万条测试订单（分布在 2 年内）
INSERT INTO "order" (user_id, order_no, status, total_amount, created_at)
SELECT
  (random() * 24 + 1)::int,
  'DEMO-' || LPAD(g::text, 10, '0'),
  CASE (random() * 4)::int
    WHEN 0 THEN 'pending'
    WHEN 1 THEN 'paid'
    WHEN 2 THEN 'shipped'
    WHEN 3 THEN 'completed'
    ELSE 'cancelled'
  END,
  round((random() * 5000 + 50)::numeric, 2),
  timestamp '2024-01-01' + random() * interval '2 years'
FROM generate_series(1, 500000) g;

-- 更新统计信息
ANALYZE "order";

-- ============ 测试 1：无索引 ============
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM "order"
WHERE created_at >= '2024-06-01'
  AND created_at < '2024-07-01';

-- ============ 创建索引 ============
CREATE INDEX idx_order_created_at ON "order"(created_at);

-- 更新统计信息（让优化器知道索引存在）
ANALYZE "order";

-- ============ 测试 2：有索引 ============
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM "order"
WHERE created_at >= '2024-06-01'
  AND created_at < '2024-07-01';

-- ============ 清理 ============
DROP INDEX idx_order_created_at;

-- 可选：删除测试数据（恢复原始 80 条记录）
-- DELETE FROM "order" WHERE order_no LIKE 'DEMO-%';
-- SELECT count(id) FROM "order";
```

## 索引失效的常见场景

建了索引不等于用得上。以下写法会让优化器放弃索引，转而走全表扫描。

| 场景 | 失效写法 | 改法 |
|---|---|---|
| 对索引列做函数运算 | `WHERE date(created_at) = '2024-06-01'` | 改成范围条件 `WHERE created_at >= '2024-06-01' AND created_at < '2024-06-02'`，或为 `date(created_at)` 建表达式索引 |
| 对索引列做算术运算 | `WHERE total_amount * 2 > 1000` | 把运算移到常量侧：`WHERE total_amount > 500` |
| 前置通配符 | `WHERE order_no LIKE '%0001'` | B-tree 只能用于前缀匹配，`LIKE 'DEMO-%'` 可以走索引；后缀/中间匹配需改用全文检索或 GIN + `pg_trgm` |
| 复合索引不满足最左前缀 | 索引为 `(user_id, created_at)`，却只查 `WHERE created_at > ...` | 调整索引列顺序，或单独为 `created_at` 建索引 |
| 数据区分度太低 | `WHERE gender = 'male'`（约命中一半行） | 优化器判断全表扫描更快，本就不该建这种索引 |
| `OR` 连接了无索引列 | `WHERE user_id = 1 OR remark = 'x'`，`remark` 无索引 | 为另一列也建索引，或改写成 `UNION` |
| 隐式类型转换 | `order_no` 是 `VARCHAR`，却写 `WHERE order_no = 12345` | 保持类型一致：`WHERE order_no = '12345'` |
| 返回行数占比过高 | 条件命中了表中大部分行 | 属于优化器的正确选择，此时全表扫描确实更快 |

最后一条值得强调：**走全表扫描不一定是坏事**。当查询要返回大部分数据时，逐条走索引再回表反而比顺序读整张表更慢，优化器放弃索引是合理决策。

## 什么时候不该建索引

- **小表**：只有几百行的表，全表扫描本来就是毫秒级，索引只会增加维护成本
- **写多读少的表**：日志写入表、消息队列表，每多一个索引写入就慢一分
- **区分度低的列**：性别、是否删除、状态只有两三种取值的列（这类列更适合做**部分索引**的过滤条件，而不是索引列本身）
- **几乎不出现在 `WHERE` / `JOIN` / `ORDER BY` 中的列**：比如只用来展示的备注、描述字段
- **已被 `PRIMARY KEY` / `UNIQUE` 覆盖的列**：约束已经自动建好索引，不要重复
- **频繁大批量导入的表**：可以先删索引，导入完成后再重建，比边写边维护更快

## 小结

| 要点 | 说明 |
|---|---|
| 索引的本质 | 一份独立维护的有序「目录」，用空间和写入性能换查询性能 |
| 默认类型 | `B-tree`，覆盖等值、范围、排序、最左前缀等绝大多数需求 |
| 特殊类型 | `GIN`（全文/JSONB/数组）、`GiST`（几何/范围/模糊）、`BRIN`（超大有序表） |
| 自动索引 | `PRIMARY KEY` 和 `UNIQUE` 自动建索引；**外键列不会**，需手动建 |
| 生产环境建索引 | 用 `CREATE INDEX CONCURRENTLY` 避免锁表 |
| 验证手段 | `EXPLAIN (ANALYZE, BUFFERS)`，重点看 `Seq Scan` 是否变成索引扫描 |
| 两个 ANALYZE | `ANALYZE 表名` 是更新统计信息；`EXPLAIN ANALYZE` 是真实执行并输出计划 |
| 常见失效原因 | 索引列被函数/运算包裹、前置通配符、不满足最左前缀、隐式类型转换 |
| 建索引的原则 | 只为高频查询条件、高区分度的列建；索引宁少勿滥 |
