## 什么是 Monorepo

**Monorepo**（单一仓库）是将多个相关的项目/包放在同一个代码仓库中管理的策略。

| Python (uv) | Node.js 对应 |
| ---- | ---- |
| `[tool.uv.workspace].members` | `pnpm-workspace.yaml` 的 `packages` |
| `[tool.uv.sources] xxx = { workspace = true }` | `"xxx": "workspace:*"` |
| `uv sync --all-packages` | 根目录 `pnpm install` |
| `uv.lock` | `pnpm-lock.yaml` |
| 根目录 `.venv` | 根目录 store + 各包 `node_modules` 链接 |
| `uv add --package <成员包>` | `pnpm --filter <成员包> add` |
| `uv run --package <成员包>` | `pnpm --filter <成员包> <script>` |
| `uv build --package <包>` | `pnpm --filter <包> build` / `turbo run build` |

```
my-monorepo/
├── packages/
│   ├── utils/          # 公共工具库
│   ├── client-sdk/     # 客户端 SDK
│   └── web-app/        # Web 应用
├── pyproject.toml      # workspace 根配置
└── README.md
```

Node.js 类比：

```js
// 常见目录（pnpm + Turborepo）
// my-monorepo/
//   apps/
//     web/       # 前端应用
//     server/    # Node.js 服务
//   packages/
//     utils/     # 公共工具包
//     core/      # 业务公共包（依赖 utils）
//   pnpm-workspace.yaml
//   package.json
//   turbo.json
```

> **说明：** Monorepo 的意义不只是「改 utils，core 能立刻联调」，还包括：一次 PR 改完整条链路（原子提交）、统一 lint/CI、重构时下游立刻报错。包之间几乎不共享时，拆成多个 Git 仓库也完全合理。

### Multirepo VS Monorepo

| 对比维度 | MultiRepo | Monorepo |
| ---- | ---- | ---- |
| **代码共享** | 需要发版、发布 pip 包才能共享 | 源码级别直接引用，即时生效 |
| **原子提交** | 跨仓库改动需要多个 PR 协同 | 一次提交完成所有关联改动 |
| **工具规范** | 各仓库独立配置工具 | 统一的工具与规范 |
| **重构成本** | 跨仓库重构代价极高 | 工具链覆盖整个仓库，安全重构 |
| **CI/CD** | 多个 Pipeline 各自独立 | 统一 CI，可增量检测受影响的包 |
| **适用场景** | 团队独立、版本节奏不一致的项目 | 紧密协作的微服务、SDK 集合、工具链 |

> **说明（多语言）：** uv workspace 只管 Python 依赖。仓库里可以同时放别的语言项目，但不要指望 `uv sync` 去装它们的依赖。多语言同仓时，各用各的包管理器，再用 Makefile / Task / CI 编排。
## 搭建 Workspace

> uv workspace 文档：https://docs.astral.sh/uv/concepts/projects/workspaces/#using-workspaces

### 第一步：初始化根项目

```shell
mkdir my-monorepo && cd my-monorepo
uv init
```

根级 `pyproject.toml`：

```toml
# 添加 members
[tool.uv.workspace]
members = [
  "packages/*",
  "app/*",
]
```

`members` 支持 glob 模式：

| 模式 | 匹配范围 |
| ---- | ---- |
| `packages/*` | `packages/` 下的直接子目录 |
| `packages/**` | `packages/` 下的所有子目录（含嵌套） |
| `libs/*` | `libs/` 下的直接子目录 |
| `apps/*` | `apps/` 下的直接子目录 |

可以同时配置多个目录：

```toml
[tool.uv.workspace]
members = [
  "packages/*",
  "apps/*",
  "libs/*",
]
```

Node.js 类比：

```js
// pnpm-workspace.yaml
// packages:
//   - 'apps/*'
//   - 'packages/*'
```

> **说明：** 根目录执行一次 `pnpm install`，会读取 workspace 内所有 `package.json`，统一解析依赖并生成一份 `pnpm-lock.yaml`。推荐习惯：永远在仓库根安装，而不是每个子包各自装一遍。

### 第二步：创建成员包

```shell
uv init --lib packages/agents
uv init --lib packages/shared
uv init app/web-service
```

Node.js 类比：

```js
// 手动或脚手架创建成员包目录，每个包自带 package.json
// packages/utils/package.json  → { "name": "@demo/utils" }
// packages/core/package.json   → { "name": "@demo/core" }
// apps/web/package.json        → { "name": "@demo/web", "private": true }
// apps/server/package.json     → { "name": "@demo/server", "private": true }
```

### 第三步：成员包依赖

```toml
# packages/agents/pyproject.toml
dependencies = [
  "shared",
]

[tool.uv.sources]
shared = { workspace = true }

# app/web-service/pyproject.toml
dependencies = [
  "agents",
]

[tool.uv.sources]
agents = { workspace = true }
```

> **`[tool.uv.sources]`** 是 UV workspace 的**核心机制**。它告诉 UV：`shared` 依赖不从 PyPI 下载，而是从工作区内的同名成员包中链接。
>
> 如果某个包在 PyPI 和 workspace 中同名，workspace 优先。需要强制走 PyPI 时可以写成 `shared = { workspace = false }`。

Node.js 类比：

```js
// packages/core/package.json
{
  "name": "@demo/core",
  "dependencies": {
    "@demo/utils": "workspace:*"
  }
}

// apps/web/package.json
{
  "name": "@demo/web",
  "dependencies": {
    "@demo/core": "workspace:*",
    "@demo/utils": "workspace:*"
  }
}
```

> **说明：** `workspace:*` 表示不要去 npm 下载，直接链接本仓库里的包。依赖方向应保持单向（如 `core → utils`），避免 A↔B 双向依赖，否则构建顺序、发版和类型循环都会出问题。需要两边共用的类型/常量时，抽第三包或下沉到更底层包。

### [可选]第四步：同步安装

```shell
uv sync --all-packages
```

执行后：

1. UV 读取所有成员包的 `pyproject.toml`
2. 解析完整的依赖树（包括成员间的依赖）
3. 在根目录生成统一的 `uv.lock`
4. 在根目录创建 `.venv`，安装所有依赖

Node.js 类比：

```js
// 根目录执行
// pnpm install
//
// 1. 读 pnpm-workspace.yaml，发现全部成员包
// 2. 收集各 package.json 依赖并统一解析
// 3. 生成根级 pnpm-lock.yaml
// 4. 在 store 中安装，并链接到各包 node_modules
```

### 第五步：运行

```shell
uv run --package web-service python app/web-service/main.py
```

Node.js 类比：

```js
// package.json（仓库根）
{
  "scripts": {
    "dev": "turbo run dev --filter=@demo/server --filter=@demo/web",
    "build": "turbo run build",
    "dev:packages": "turbo run dev --filter=@demo/utils --filter=@demo/core"
  }
}

// 常用命令
// pnpm dev              // 同时起 server + web
// pnpm --filter @demo/web dev
```

### [可选]使用 Makefile

```makefile
.PHONY: run-web

run-web:
  uv run --package web-service python app/web-service/main.py
```

Node.js 类比：

```js
// 根 package.json 的 scripts 通常就承担 Makefile 角色
{
  "scripts": {
    "dev": "turbo run dev --filter=@demo/server --filter=@demo/web",
    "build": "turbo run build"
  }
}
```

### [可选]安装第三方依赖

```shell
# 给某个成员包添加依赖
uv add --package <成员包> <包名>

# 给项目根添加依赖
uv add --dev <包名>
```

Node.js 类比：

```js
// 给某个成员包加依赖
// pnpm --filter @demo/web add react
// pnpm --filter @demo/web add -D vite typescript

// 给仓库根加整仓工具
// pnpm add -Dw turbo
```

### 根包放什么，子包放什么

| 放哪里 | 放什么 |
| ---- | ---- |
| **根 `pyproject.toml`** | 工作区配置、整仓开发工具、根级脚本 |
| **成员包自己的 `pyproject.toml`** | 该包真正用到的运行时/测试/构建依赖 |

原则：**谁用到依赖，就写在谁的配置里。**

- 某个服务用到 `fastapi` → 写在该服务成员包
- 测试库同理：谁跑测试，谁声明 `pytest`
- 多个成员都要用同一工具时，目标是**版本统一**，不是「只写在根上让大家偷用」

Node.js 类比：

```js
// 根 package.json：只放整仓工具
{
  "private": true,
  "devDependencies": {
    "turbo": "^2.5.4",
    "typescript": "^5.8.3"
  }
}

// apps/web/package.json：业务与框架依赖写在自己这里
{
  "dependencies": {
    "react": "^18.3.1"
  },
  "devDependencies": {
    "typescript": "^5.8.3",
    "vite": "^6.3.5"
  }
}

// 多个前端要对齐版本时：各自声明依赖，用 pnpm catalog 统一版本号
```

> **说明：** 子包各自声明 `typescript`，不等于磁盘上装很多份；pnpm 会去重。但声明必须有，因为默认隔离：没写在自己 `package.json` 里的包，运行/构建时通常找不到。
### 依赖隔离

uv workspace 同步后，常见是根上一个 `.venv`，成员包处在更偏共享的环境里——体感上有时「环境里已经有了」就能 import。写依赖时仍应在各自 `pyproject.toml` 里声明清楚，但隔离边界不如前端包管理器那么硬。

Node.js 类比：

```js
// pnpm 默认更严：A 包装的依赖，B 包不能直接用
// @demo/core 声明了 dayjs，并不代表 @demo/utils 能用
// packages/utils 里直接 import "dayjs" → 通常失败
// utils 要用 dayjs，必须写进自己的 package.json
// 目的是消灭「幽灵依赖」（没声明却能 import）
```

### [可选]构建

```shell
# 构建全部
uv build

# 构建指定包
uv build --package utils
```

Node.js 类比：

```js
// 构建全部（turbo 会按 ^build 先构建被依赖的包）
// pnpm build

// 构建指定包
// pnpm --filter @demo/utils build
// pnpm --filter @demo/core build
```

> **说明（和 uv 很不一样的一点）：** uv 的 workspace 源码链接，改成员包源码通常立刻对依赖方生效。Node.js 侧若公共包 `exports` 指向 `dist`（如 tsup 产物），改 `src` **不会**自动反映到 web/server，需要先 `pnpm --filter @demo/core build`，或单独跑 `pnpm dev:packages`（`tsup --watch`）。`apps/web`（Vite）和 `apps/server`（tsx watch）本身会热更新，但 `packages/*` 不会。

### [可选]查看依赖关系

```shell
# 查看 workspace 中某个包的依赖树
uv tree --package web-app

# 查看所有包的依赖树
uv tree
```

输出示例：

```
web-app v0.1.0
├── data-tools v0.1.0 (workspace)
│   └── pandas v2.1.0
│       ├── numpy v1.26.0
│       └── python-dateutil v2.8.2
└── utils v0.1.0 (workspace)
```

workspace 中的包会标记为 `(workspace)`，一目了然。

Node.js 类比：

```js
// 查看某包依赖
// pnpm --filter @demo/web list --depth 1

// 依赖关系示意（与当前 demo 一致）
// @demo/utils
// @demo/core → @demo/utils (workspace)
// @demo/server → @demo/core, @demo/utils
// @demo/web → @demo/core, @demo/utils
```

## 包间依赖的三种模式

### 源码链接（workspace 模式）

```toml
[tool.uv.sources]
utils = { workspace = true }
```

- 本地直接引用源码，修改即时生效
- 无需 `pip install -e .` 或 `uv add` 重新安装
- 适合日常开发

Node.js 类比：

```js
{
  "dependencies": {
    "@demo/utils": "workspace:*"
  }
}
```

> **说明：** 协议上都是「链到工作区内的包」。uv 更常直接吃源码；pnpm + 构建型公共包时，链到的往往是包入口（常为 `dist`），开发期要配合 watch/build。

### 路径引用

```toml
[tool.uv.sources]
utils = { path = "../utils" }
```

- 引用工作区之外的本地包
- 路径可以是相对或绝对路径

Node.js 类比：

```js
{
  "dependencies": {
    "@demo/utils": "file:../utils"
  }
}
```

### Git 引用

```toml
[tool.uv.sources]
utils = { git = "https://github.com/org/utils.git", rev = "v0.1.0" }
```

- 引用 Git 仓库中的某个版本
- 可用于引用未发布到 PyPI 的依赖

Node.js 类比：

```js
{
  "dependencies": {
    "@demo/utils": "github:org/utils#v0.1.0"
  }
}
```
